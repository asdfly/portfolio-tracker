## 第三部分 · 分层整合方案

> 原则：**先保全、再入库、后打通**；每层独立可交付、可回滚，互不阻塞。

### Tier 0｜资产保全 🔴 P0（最高优先级，建议立即执行）

**问题**：R1 无版本控制，1395 条行业-日记录 + 45 日风格轨迹存于会话目录，一旦清理即永久丢失。

**方案**：在 portfolio_tracker 建立 `research/sector_rotation/` 归集目录，纳入 git：

```
research/sector_rotation/
├── history.json              # 快照库（557 KB，含 45 日全量行业数据）
├── dashboard.html            # 仪表盘当前版本
├── reviews/                  # 周度/月度复盘（11 份）
├── mail_body/                # 邮件正文（8 份）
└── scripts/                  # canonical 脚本（从 58 个临时脚本中甄别）
    ├── _build_mail_body.py   # 邮件正文生成（canonical）
    ├── _snap_dump.js         # SNAPS → JSON 抽取
    └── _append_hist.py       # history.json 追加（统一命名）
```

**执行**：一次性复制 + `git add`（显式路径）+ commit。**每日增量同步**交由投研线自动化在写完 `history.json` 后追加一步复制（幂等覆盖）。

**验收**：`git ls-files research/sector_rotation/ | wc -l` ≥ 20；`git log` 可见归集提交。

### Tier 1｜数据入库 🔴 P0

**问题**：投研线数据仅存在于 JSON，无法与持仓联合查询；组合线行业数据不全（13/31）。

**方案**：在 `portfolio.db` 新建 3 张表（沿用现有表命名与 `created_at` 惯例），并回填 45 日历史：

| 新表 | 字段 | 回填行数 |
|---|---|---|
| `sector_fund_flow` | `date, sector_name, change_pct, main_net_inflow, volume_change, turnover_rate, is_core, source, created_at` | 45 × 31 ≈ **1395** |
| `northbound_daily` | `date, total_amount, pct_of_market, nb_top_json, is_disclosed, source, created_at` | **45** |
| `style_compass` | `date, x_largecap_to_smallcap, y_growth_to_value, source, created_at` | **45** |

**数据源权威性约定**：以 `history.json` 为唯一回填源（其为每次运行的落盘产物，已过 f 求和自洽校验），不重新联网抓取，避免引入口径漂移。

**增量**：投研线自动化每日写入 `history.json` 后，追加一步 `scripts/research/sync_rotation_to_db.py --date <当日>`（幂等 upsert，按 `date + sector_name` 唯一键）。

**验收**：`SELECT COUNT(*) FROM sector_fund_flow` ≥ 1395；`SELECT MAX(date)` = 2026-10-13；随机抽 3 日核对 `f` 求和 ≈ 该日全市场主力净流入。

### Tier 2｜脚本固化 🟡 P1

**问题**：R2 根目录 58 个一次性脚本，canonical 脚本无标识，历史反复踩坑（10-12 曾误判 `_build_mail_body.py` 缺失）。

**方案**：
1. 从 58 个脚本中甄别 canonical 脚本（当前识别为 `_build_mail_body.py`、`_snap_dump.js`、`_append_hist_*.py` 系列）→ 迁入 `research/sector_rotation/scripts/` 并**去掉日期后缀**（统一命名）；
2. 一次性脚本（`_validate_*`、`_check_*`、`_extract_*`、`_probe_*`、`_inject_*`、`_fetch_*` 等按日期命名者）→ 保留在投研工作区，不入库，随会话自然淘汰；
3. 在 `scripts/research/` 下新建 `sync_rotation_to_db.py`（Tier 1 增量同步脚本）。

**验收**：`research/sector_rotation/scripts/` 下 3 个 canonical 脚本可执行（`--help` 通过）；投研线自动化 prompt 中的路径引用同步更新。

### Tier 3｜配置解耦 🟡 P1

**问题**：R3 跨工作区 `.env` 依赖。

**方案**：在投研工作区放置**专用 `.env`**（复制 `EMAIL_*` 六个键），`_build_mail_body.py` 的 `ENV_PATH` 与自动化 prompt 改为指向本工作区 `.env`。
**注意**：`.env` 含凭据，**不入库**（确认 `.gitignore` 已覆盖 `*.env`；投研工作区非 git 仓库，天然安全）。

**验收**：投研线邮件发送成功且 `ENV_PATH` 不含 `portfolio_tracker` 字样。

### Tier 4｜分析能力打通 🟡 P2（价值最高，但需先解决口径问题）

**愿景**：回答组合线目前无法回答的问题——「**今天组合的涨跌，是哪些行业贡献的？资金正在流入还是流出我重仓的行业？**」

**链路**：
```
portfolio_snapshots(持仓市值)
  → etf_industry_alloc(ETF→行业权重)
  → sector_fund_flow(行业日度涨跌/资金流)
  → 组合行业暴露归因 + 资金流贡献度
```

#### ⚠️ 方法论自审：口径障碍（必须显式承认，不可回避）

| 环节 | 口径 | 问题 |
|---|---|---|
| `etf_industry_alloc` | **证监会门类**（如「制造业」「信息传输、软件和信息技术服务业」「房地产业」「科学研究和技术服务业」） | 粒度粗，且 `report_date = 2026-03-31` 为季报口径，**滞后约 6 个月** |
| 投研线 SECTORS | **申万一级 31 行业**（通信/电子/传媒/计算机/医药生物…分列） | 粒度细 |

**二者是不同分类体系，且映射为「一对多」并带信息损失**：证监会「制造业」无法精确拆分为申万的 电子/电力设备/机械设备/汽车/家用电器/食品饮料/医药生物/基础化工 等。

**可选路径（需你拍板）**：

- **方案 A（保守·推荐先做）**：归因停留在**证监会门类级**。投研线 31 行业数据向上聚合到门类，与 `etf_industry_alloc` 对齐。**优点**：口径严格、无编造；**缺点**：颗粒度粗（约 10 余个门类）。
- **方案 B（激进）**：借道 `etf_top_holdings`（**个股级**，270 行）→ 个股映射到申万 31 行业 → 精确行业暴露。**优点**：颗粒度达申万 31 行业；**缺点**：① 仅覆盖部分 ETF 的**前十大重仓**（非全持仓，权重覆盖不完整）；② 需维护个股→申万行业映射表；③ 10-13 数据显示 `etf_top_holdings` 最新为 09-25，滞后。
- **方案 C（暂缓）**：等待 `etf_industry_alloc` 更新到 Q3 报告期，再评估。

**建议**：先做方案 A（口径安全、可立即交付），若 A 的归因洞察力不足，再评估 B 的投入产出。

### Tier 5｜报告联动 🟢 P2（可选，需你决策）

**现状**：18:00 组合盘后日报 + 18:15 行业轮动仪表盘 = **两封独立邮件**。

**选项**：

| 选项 | 做法 | 优缺点 |
|---|---|---|
| **① 保持现状**（推荐） | 两封独立，维持 18:00 / 18:15 错峰 | ✅ 职责清晰、互不阻塞、单封失败不影响另一封；❌ 收两封邮件 |
| ② 合并为综合邮件 | 单一邮件含「组合持仓 + 市场行业」双板块 | ✅ 一封读完；❌ 耦合度高，任一环节失败导致整体延迟；❌ 改造量大 |
| ③ 组合日报内嵌行业摘要 | 组合邮件增加「今日行业资金流 Top5」板块（数据来自 Tier 1 新表） | ✅ 增量小、风险低、信息增益明显；❌ 与轮动邮件仍有部分重复 |

**建议**：采用 **① + ③**——保持两封独立投递（可靠性优先），同时在组合日报中增加一小段行业资金流摘要（来自 Tier 1 入库数据，无需联网），实现"轻联动"。
